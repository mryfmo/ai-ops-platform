# ADR-0008: Excelインポートはexceljsと冪等ジョブキューで実装する

## ステータス

採用

## コンテキスト

- PrjOpsの初期登録や一括更新では、Issue、Project v2アイテム、milestoneをExcelから取り込む要件がある。
- `docs/research/2026-07-09-deep-research.md` は、既存OSSのGitHub issue importツールがProjects v2や冪等性を満たさないこと、npm `xlsx` がCVE-2024-22363未修正であること、GitHubのコンテンツ生成系セカンダリリミットが大規模インポートの律速になることを確認している。
- `docs/research/2026-07-09-charts-and-design.md` は、`exceljs` 4.4.0 の最終リリースが 2023 年で保守活性が低下している一方、確認時点で未修正 advisory がなく、npm `xlsx` より安全な選択であると整理している。この前提は劣化しており、信頼できないファイルへの入力検証と定期的な依存棚卸しを継続する必要がある。
- 予定仕様ID: PrjOps `REQ-037` / `SPEC-INT-063` / `AC-037-1`。実装コード参照を追加しない本ADR段階では、`REQ`/`SPEC-INT` のspec-id登録は実装フェーズへ送る。

## 決定

- Excel読み取りライブラリは `exceljs` を採用する。npm `xlsx` はCVE-2024-22363が恒久未修正であるため採用しない。
- インポート対象はIssue、Project v2アイテム、milestoneに限定する。PRはコード変更から生成されるレビュー単位であり、データ登録対象として不適切なのでExcelインポート対象外とする。
- 冪等性の正本はインポート台帳テーブルとする。Issue bodyのimport markerは人間がGitHub画面で由来を確認するための追跡マーカーであり、既存Issue検索による重複防止の第二防御としては扱わない。
- GitHub書き込みはジョブキュー化し、Project v2の `addProjectV2ItemById` → `updateProjectV2ItemFieldValue` の2段ミューテーションと、コンテンツ生成80/分・500/時のセカンダリリミットを前提に進捗制御する。
- ユーザーにはジョブ進捗レポートと、行番号付きのバリデーションエラーレポートを返す。
- 取り込みテキストは保存前、GitHub送信前、レポート表示前の3箇所で既存サニタイズ規約を通す。

## 根拠

- Excelインポートは再実行される運用が自然であり、タイトル一致などの曖昧な重複判定ではデータ破壊や重複作成を避けられない。
- Project v2登録はアイテム追加とフィールド更新を1ミューテーションで完結できないため、ユーザー操作を同期的に待たせるよりジョブキューで進捗を返す方がGitHub制限に合う。
- PRをExcelから作ると、差分・レビュー・CIというPR本来の由来と監査性が崩れる。インポート対象をデータ登録物に限定する方が権限境界も単純になる。

## 影響

- Excelテンプレートには安定キー列が必須になる。
- import ledgerテーブルとジョブ状態テーブルが必要になる。
- 大量インポートは即時完了ではなく、進捗確認とエラー修正を前提とする。
- `exceljs` の保守活性・advisory を四半期の依存棚卸しで再確認する。代替ライブラリへの移行や新規依存追加は本ADRでは行わない。
