## A. レビューが見落としていた所見

### ADV-VER-014 [High] 正本 PRD に定義された受入条件が spec-ids・カタログの双方に存在せず、機械検証の外にある

- 実証: `docs/spec/prjops/03_PRD.md:104,105,109` は `AC-011〜015共通-1`、`AC-011〜015共通-2`、
  `AC-016-1` を定義する。`packages/traceability/spec-ids/prjops.json` の AC 39 件にも
  `docs/spec/spec-id-catalog.md` にも、この 3 件は存在しない（カタログは `AC-010-3` から
  `AC-017-1` へ飛ぶ）。
- 原因は 2 系統ある。
  - `AC-016-1` は**登録漏れ**。ID 書式はツールの文法（`AC-\d{3}(?:-\d+|[a-z])?`）に適合する。
  - `AC-011〜015共通-*` は**文法が表現できない**。範囲記法を ID として書けない。
- 構造的な穴: カタログガードは spec-ids ↔ カタログを突合するだけで、**正本（PRD）↔ spec-ids を
  突合しない**。したがって PRD にしか存在しない ID は、どちらのガードにも掛からず永久に不可視になる。
  04 章 ADV-VER-006（disposition が欠落 ID と連動しない）より 1 段深い層の問題である。
- 影響: `AC-011〜015共通-1` は「各プロファイルのレポートに非表示指定の情報が一切含まれない」という
  **権限フィルタの受入条件**（AGENTS.md 設計原則 6 の中核）であり、`packages/prjops/src/lib/reportPermissionFilter.ts`
  から参照されているにもかかわらず、トレーサビリティ上は存在しない。
- 是正方向: **仕様側の裁定が要る（未裁定）。** 選択肢は次の 3 つで、いずれも本書の執筆時点では
  決まっていない。**推測で ID を書き換えても登録してもならない。** 工数 S（裁定後）。

  1. PRD 側を展開する。**`共通-1` と `共通-2` は別条件なので両系列が要る** — `AC-011-1`〜`AC-015-1`
     と `AC-011-2`〜`AC-015-2` の計 10 件。片系列だけ展開すると、もう一方が未登録のまま残り、
     本節が指摘した穴を半分残すことになる。既存文法のまま扱えるが、正本の文面が変わる。
  2. ツールの ID 文法へ範囲記法を追加する。正本は不変だが、文法が複雑化し他の突合にも影響する。
  3. 各系列を代表 ID 1 件へ正規化する。変更は最小だが、範囲が指す残り 4 プロファイル分は
     引き続き不可視のまま残る（両系列を正規化しても計 2 件しか登録されない）。

  あわせて「正本（PRD）↔ spec-ids を突合するガードを足すか」も判断が要る。足せば同種の漏れは
  今後発生しなくなるが、PRD の見出し記法に依存する抽出になるため脆い。

### ADV-VER-015 [Medium] 実在しない ID を引く根拠ヘッダが 2 件あり、いずれもガードを通過していた

- 実証: `packages/devops/src/db/migrate.ts` の `根拠: A-11`（どの ID 体系にも属さない文字列）、
  および `packages/prjops/src/templates/index.ts` の `AC-016-1`（上記のとおり未登録）。
- 通過した理由は 2 つ重なる。(a) 根拠ヘッダガードの走査範囲が `shared/src/reporting` と
  `server/src` の 2 箇所だけで、`devops/src`・`prjops/src` は対象外だった（ADV-VER-005）。
  (b) 名前空間ガードは bare 未知 ID を検出しない（ADV-VER-004）。
- 影響: 実在しない ID を引く根拠ヘッダは、「その受入条件は実装・検証済み」という**偽の証跡**を作る。
- 是正は A028（`agent/a028-basis-header-scope`）。**本追補の時点では未マージであり、`main` の
  `basisHeaderFailures()` は依然として 2 ディレクトリしか走査せず、上記 2 ヘッダも未修正のまま
  残っている。** 同ブランチでは走査範囲を全パッケージ `src/` へ拡大し、両ヘッダを是正している。
  `AC-016-1` は上記の裁定が未了のため ID 参照を外し、検証している事実だけを残す扱いとした。

## C. 是正作業そのものから得られた知見

レビュー本体は「所見を直せば解決する」という前提で書かれているが、実装してみると
**是正が新しい失敗様式を生む**ことが 2 度あった。いずれも独立レビュー（Codex）が検出した。

1. **coding-task reaper の相関キー**: 実行状態を観測するため run を `agent/<task_id>` ブランチで
   引いたが、dispatch の `ref` は `main` であり作業ブランチは run に紐づかない。照会は常に空を返し、
   **全 stale 行が「run 皆無」として誤って回収される**状態になっていた。観測したふりをする分、
   経過時間だけで判断していた元の実装より悪い。
2. **dispatch 不確定時の終端**: 「不確かなら再実行させない」は reaper を入れる前なら妥当だが、
   入れた後は誤り。running のまま残せば二重起動は claim 条件で防げ、実際に run が出たかは
   reaper が観測して安全に終端できる。

**教訓**: 自分の修正が生んだ失敗様式は自分では見えにくい。所見の是正には、実装とは独立した
レビュアーに「この修正は本当に効いているか」を問わせる往復を、修正のたびに回す必要がある。
PR #128 は 6 巡・15 スレッドを要し、うち上記 2 件は**修正自体が機能していない**という指摘だった。
