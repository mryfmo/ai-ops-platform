# 文書2: PRD（Product Requirements Document）AIエージェント主導DevOps運用基盤

- 文書ID: DOC-PRD-02
- 版: 1.0（2026-07-03）
- 対象読者: 後続実装モデル（Claude Opus 4.8 / Claude Sonnet 5）、プロジェクト責任者
- 上位文書: DOC-ANL-01（現状分析・再設計書。閾値TH-、重大度Sev、エージェントAGT-、プロファイルPRF-の定義はDOC-ANL-01を正とする）
- 下位文書: DOC-EXT-03（外部仕様書）、DOC-INT-04（内部仕様書）

## 1. 目的と背景

人手中心のDevOps運用（DOC-ANL-01第1章の課題ISS-01〜ISS-08）を、AIエージェント主導の運用基盤（以下「本システム」）に置き換える。対象はプロジェクト約50件、関係者は社内3プロファイル（PRF-M/PRF-L/PRF-G）および国内外の関連企業数十社。

## 2. スコープ

- 対象: CI/CD、環境構築、リリース管理、インシデント対応、監視・アラート対応、権限管理、プロファイル別定期報告。
- 対象外: 人事評価、契約管理、開発手法（アジャイル等）自体の変更。
- 連携必須ツール: GitHub（Actions/リポジトリ/Issue/PR）、Microsoft Teams、Outlook、Claude Code。

## 3. 要件定義

各要件は「要件ID／要件／受け入れ基準（AC）」で構成する。ACはすべて検証可能な合否条件である。実装時、1つのREQに複数の実装解釈が成立する場合は、外部仕様書・内部仕様書の対応IDの記述を優先し、それでも曖昧な場合は実装せずOPEN課題として報告すること。

### 3.1 CI/CD・ビルド監視（AGT-BLD）

**REQ-001 ビルド失敗の自動一次調査**
GitHub Actionsのワークフロー失敗時、AGT-BLDが失敗ログを解析し、原因分類（後述の5分類）と該当箇所の要約をPRコメントおよびTeams通知として出力する。
- AC-001a: ワークフロー失敗イベント受信から10分以内に、PRコメントとTeams通知の両方が出力される（テストで失敗を10件発生させ、10件すべてで達成）。
- AC-001b: 原因分類は「テスト失敗／コンパイルエラー／依存関係／インフラ・タイムアウト／不明」の5値のいずれかで出力される。
- AC-001c: 分類「不明」の比率が検証用データセット50件中20%以下。

**REQ-002 修正案の自動生成**
原因分類が「テスト失敗」「コンパイルエラー」の場合、AGT-BLDはClaude Codeを呼び出し修正案（diff形式）をPRコメントに添付する。修正の自動コミットは行わない（人間がレビューして適用する）。
- AC-002a: 対象2分類の失敗10件中8件以上でdiff形式の修正案が出力される。
- AC-002b: 修正案がリポジトリへ自動コミット・自動マージされないことをテストで確認。

**REQ-003 ステージング自動昇格**
TH-001を充足したコミットは、AGT-DEPが人間の承認なしでステージング環境へデプロイし、結果をTeamsに事後通知する。
- AC-003a: TH-001充足ケースで昇格が実行され、非充足ケース（カバレッジ79%等の境界値を含む）で実行されないことを境界値テストで確認。
- AC-003b: 昇格完了から5分以内にTeams通知が送信される。

### 3.2 リリース管理・デプロイ判断（AGT-DEP、AGT-CHG）

**REQ-010 本番デプロイの人間承認**
本番デプロイは、AGT-CHGが生成する承認パッケージ（変更差分要約・テスト結果・リスクスコア・ロールバック手順）をTeamsアダプティブカードで提示し、リーダー以上の承認（TH-002）を得た場合のみAGT-DEPが実行する。
- AC-010a: 承認なしで本番デプロイが実行される経路が存在しないこと（コードレビューおよび権限テストで確認）。
- AC-010b: TH-002の時限（30分でエスカレーション、60分で自動中止）が動作することをタイマーテストで確認。
- AC-010c: 承認者がメンバー権限の場合、承認操作が拒否される。

**REQ-011 リスクスコアリング**
承認パッケージのリスクスコアは0〜100の整数で、算出式は内部仕様書SPEC-INT-021に定義するものを唯一の実装とする。
- AC-011a: 同一入力に対しスコアが決定的（同値）であること。
- AC-011b: スコア70以上の場合、承認カードに「高リスク」バッジが表示される。

**REQ-012 自動ロールバック**
TH-003充足時、AGT-DEPは人間の承認なしで直前の安定バージョンへロールバックし、Sev2インシデントとして起票、Teamsへ即時通知する。
- AC-012a: TH-003の(a)(b)それぞれを模擬した負荷テストでロールバックが発動する。
- AC-012b: 発動から2分以内にTeams通知とGitHub Issue起票が完了する。
- AC-012c: ロールバック先バージョンが「直前に本番で15分以上安定稼働したバージョン」であることをテストで確認。

### 3.3 インシデント対応・監視（AGT-INC）

**REQ-015 一次切り分けの自動化**
監視アラート・外部企業からの障害連絡（Teams/メール）を受信したAGT-INCは、TH-004のSLA内に重大度分類（Sev1〜4）、影響プロジェクト推定、GitHub Issue起票、Teams通知を行う。
- AC-015a: 検証用アラート30件で、受信から5分以内の処理完了率100%。
- AC-015b: 重大度分類の一致率（人間の正解ラベルとの比較）が30件中80%以上。
- AC-015c: Sev1はAGT-INCが「Sev1候補」として提示し、人間の宣言操作なしにSev1として確定しない。

**REQ-016 時限エスカレーション**
TH-005に従い、未応答時の自動エスカレーションを行う。
- AC-016a: Ackなし10分でリーダー、20分でマネージャーへ通知されることをタイマーテストで確認。
- AC-016b: Ack済みの場合エスカレーションが停止する。

**REQ-017 誤検知の抑制**
TH-006充足のアラートは自動クローズ候補とし、人間の確認（24時間以内）を経てクローズする。確認がない場合はオープンのまま維持する。
- AC-017a: TH-006充足ケースが候補化され、非充足ケースが候補化されないことを確認。
- AC-017b: 人間確認なしで自動クローズされないことを確認。

### 3.4 権限管理（AGT-SEC）

**REQ-018 JIT権限付与と自動失効**
権限申請はAGT-SECが受け付け、妥当性チェック（申請者の所属プロジェクト、申請理由の必須入力、既存権限との重複）を行った後、人間承認（開発・ステージング＝リーダー、本番・外部企業＝マネージャー）を経て付与する。失効はTH-007に従う。
- AC-018a: 本番権限が付与から8時間で自動失効することをテストで確認。
- AC-018b: 外部企業アカウントが90日で失効し、再承認なしに延長されないことを確認。
- AC-018c: 人間承認なしで権限が付与される経路がないこと。

**REQ-019 月次棚卸し**
AGT-SECは毎月第1営業日に全権限の棚卸しレポート（保有者・権限・最終利用日・失効予定日）を生成し、マネージャーへOutlook配信する。
- AC-019a: レポートに全アクティブ権限が漏れなく含まれる（テストデータ100件で欠落0）。

### 3.5 プロファイル別定期報告（AGT-RPT）

3プロファイルの要件を分離して定義する。共通部分と差分部分を明示する。

**REQ-020 共通要件**
レポートはHTML形式で生成し、Outlookメール本文として配信する。データ集計期間・生成時刻をヘッダーに明記する。レイアウト・データ項目の詳細は外部仕様書SPEC-EXT-020〜026に従う。
- AC-020a: 主要メールクライアント（Outlookデスクトップ／Web）で表示崩れがない（レンダリング確認）。
- AC-020b: レポート内の数値がソースデータ（GitHub/監視/インシデントDB）と一致する（サンプル10項目の突合で不一致0）。

**REQ-021 PRF-M（メンバー）向け**
粒度: 自分が担当するタスク・PR単位。頻度: 毎営業日09:00 JST（日次）。内容: 自分のオープンPRとCI状態、自分宛レビュー依頼、自分が当番のアラート未対応一覧。閲覧権限: 本人の担当分のみ（他人の個人別データは含めない）。
- AC-021a: 配信時刻が09:00 JST±5分以内。
- AC-021b: 他メンバーの個人別タスクデータが含まれない。

**REQ-022 PRF-L（リーダー）向け**
粒度: 担当プロジェクト単位。頻度: 日次（09:00 JST）＋週次（月曜09:00 JST）。内容: プロジェクトのCI成功率、デプロイ実績、オープンインシデント、承認待ち一覧、メンバー別ではなくタスク種別別の滞留状況。閲覧権限: 担当プロジェクトのみ。
- AC-022a: 担当外プロジェクトのデータが含まれない。

**REQ-023 PRF-G（マネージャー）向け**
粒度: 全50プロジェクト横断の健全性指標。頻度: 週次（月曜09:00 JST）＋月次（第1営業日09:00 JST）。内容: プロジェクト横断のDORA指標（デプロイ頻度、変更リードタイム、変更失敗率、MTTR）、Sev1/Sev2一覧、権限棚卸しサマリ、要注意プロジェクトTop5。
- AC-023a: 50プロジェクト全件が集計対象に含まれる。
- AC-023b: DORA4指標すべてが数値で表示される。

**REQ-024 配信先管理**
プロファイルと配信先の対応はAGT-SECが管理する名簿を唯一のソースとし、名簿変更は翌日の配信から反映される。
- AC-024a: 名簿から削除された宛先に配信されない。

### 3.6 連携・非機能要件

**REQ-025 GitHub連携**: リポジトリイベント（push、workflow_run、PR）をWebhookで受信し、Issue/PRコメント・デプロイをGitHub API経由で実行する。
- AC-025a: Webhook受信からエージェント処理開始まで60秒以内。

**REQ-026 Teams/Outlook連携**: 通知・承認はTeams（アダプティブカード）、定期報告・棚卸しはOutlook（Microsoft Graph API）で行う。
- AC-026a: 承認カードのボタン操作が監査ログに操作者IDと共に記録される。

**REQ-027 多言語通知**: 外部企業向け通知（SPEC-EXT-030番台）は日本語・英語の2言語で送信できる。企業ごとの言語設定に従う。
- AC-027a: 言語設定ENの企業に英語通知が送信される。

**REQ-028 監査ログ**: すべてのエージェント判断・人間承認・権限操作を追記専用ログに記録し、1年間保持する。
- AC-028a: 任意の本番デプロイについて「誰が承認し、どの基準で実行されたか」をログのみから再構成できる。

**REQ-029 可用性・失敗時挙動**: エージェント自体が停止した場合、フェイルセーフとして (a) 自動デプロイ・自動クローズ等の能動的操作は停止し、(b) GitHub Actions等の既存パイプラインは従来どおり人間が手動運用できる状態を維持する。
- AC-029a: エージェント停止状態で手動デプロイ手順（内部仕様書SPEC-INT-060）が実行可能。

**REQ-030 秘密情報**: シークレット（APIキー等）を平文でログ・レポート・PRコメントに出力しない。
- AC-030a: 検証用シークレット文字列がすべての出力経路に現れないことをテストで確認。

## 5. リスクと前提

- 現状分析が標準参照モデルに基づく点（DOC-ANL-01第0章、残課題OPEN-001）。
- AIの重大度分類・原因分類には誤りが残るため、AC-001c/AC-015bの精度基準を下回る場合は人間レビューを必須とするフォールバックを維持する。
