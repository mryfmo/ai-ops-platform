## 0. 本書の前提と制約（必読）

本書の「現状分析」は、依頼者固有の社内資料（既存の運用手順書、体制図、実際のインシデント記録等）が提供されていないため、**依頼時に明示された前提条件（プロジェクト約50件、国内外関連企業数十社、GitHub / Microsoft Teams / Outlook / Claude Code を利用）に基づく、人手中心DevOps運用の標準参照モデル**として記述している。実在組織の現状と差異がある場合は、本書の第1章を実態に合わせて更新した上で、PRD以降の文書の該当IDを見直すこと。この検証作業は残課題 OPEN-001 として最終報告に記載する。

用語・IDは全文書で共通とする（第4章の用語集を正とする）。

## 1. 現状分析（As-Is: 人手中心のDevOps業務プロセス）

### 1.1 対象業務領域

| 領域ID | 業務領域 | 現状の主担当 |
|---|---|---|
| AR-01 | CI/CD（ビルド・テスト・デプロイパイプライン） | 各プロジェクトの開発リーダー |
| AR-02 | 環境構築（開発／ステージング／本番） | インフラ担当メンバー |
| AR-03 | リリース管理（リリース判定・承認・実施） | リーダー＋マネージャー |
| AR-04 | インシデント対応（検知・切り分け・復旧） | 当番メンバー（オンコール） |
| AR-05 | 監視・アラート対応 | 当番メンバー |
| AR-06 | 権限管理（リポジトリ・環境・外部企業アカウント） | マネージャー＋情報システム担当 |
| AR-07 | 定期報告（進捗・健全性の報告） | リーダーが手作業で作成 |

### 1.2 関係者と役割（現状）

| 役割 | 人数規模（想定） | 現状の主な責務 |
|---|---|---|
| メンバー | 各プロジェクト2〜5名 | 実装、PR作成、当番対応、ビルド失敗の調査 |
| リーダー | 各プロジェクト1名 | リリース判定、レビュー、週次報告作成、エスカレーション一次受け |
| マネージャー | 複数プロジェクト横断で数名 | 本番リリース最終承認、権限承認、対外調整、経営報告 |
| 関連企業担当者（国内外・数十社） | 各社1〜数名 | 仕様調整、受け入れ確認、障害時の連絡窓口 |

### 1.3 現状の業務フロー・意思決定ポイント・情報の流れ

各領域の現状フローを「ステップ／担当／意思決定ポイント／使用ツール」で示す。

#### AR-01 CI/CD
1. メンバーがGitHubへpush、PRを作成（GitHub）。
2. GitHub ActionsがCIを実行。失敗時はメンバーが手動でログを確認し原因を調査（属人的、平均調査時間はプロジェクトにより大きくばらつく）。
3. リーダーが手動でPRをレビューし、マージ可否を判断（意思決定ポイントDP-01）。
4. ステージングへのデプロイはリーダーが手動トリガー（DP-02）。

#### AR-03 リリース管理
1. リーダーがリリース候補をまとめ、Teamsチャットでマネージャーへ承認依頼。
2. マネージャーが口頭・チャットで承認（DP-03。承認基準が文書化されておらず個人判断）。
3. メンバーが手動で本番デプロイを実施。深夜・休日リリースは特定メンバーに集中。
4. 障害発生時のロールバック判断はその場の合議（DP-04。基準なし）。

#### AR-04 / AR-05 インシデント・監視
1. 監視ツールまたは関連企業からのメール／Teams連絡で異常を検知。
2. 当番メンバーが一次切り分け（影響範囲・重大度の判断が属人的。DP-05）。
3. 重大時はリーダー→マネージャーへ電話・チャットでエスカレーション（基準・時限なし）。
4. 対応記録は事後にまちまちの形式で残される（ナレッジが蓄積されない）。

#### AR-06 権限管理
1. 権限付与依頼はメール・Teamsで随時発生（国内外数十社の外部アカウントを含む）。
2. マネージャーが都度判断して付与（DP-06）。棚卸しは年1回未満。付与済み権限の失効漏れが常態化。

#### AR-07 定期報告
1. リーダーが各ツールから手作業で情報を収集し、Excel/PowerPointで報告資料を作成（1人あたり週2〜4時間）。
2. プロファイル別（メンバー／リーダー／マネージャー）の情報粒度の出し分けは行われておらず、全員に同一資料が配布される。

### 1.4 現状の課題一覧

| 課題ID | 課題 | 影響 |
|---|---|---|
| ISS-01 | ビルド失敗調査が属人的で、一次調査の着手が遅い | リードタイム悪化 |
| ISS-02 | リリース承認基準が非文書化・個人判断 | 品質のばらつき、監査不能 |
| ISS-03 | ロールバック発動基準がなく合議で遅延 | 障害影響の長期化 |
| ISS-04 | 一次切り分けの品質が当番個人に依存 | MTTR悪化、誤エスカレーション |
| ISS-05 | エスカレーションの時限・経路が未定義 | 重大障害の報告遅延 |
| ISS-06 | 権限付与が場当たり的、棚卸し不備、外部企業アカウントの失効漏れ | セキュリティリスク |
| ISS-07 | 定期報告が手作業・単一粒度で高コスト | リーダー工数の浪費、マネージャーが横断状況を把握できない |
| ISS-08 | 50プロジェクト規模で上記が同時多発し、人手では標準化・スケールが不可能 | 全体 |

## 2. 再設計（To-Be: AIエージェント主導のDevOps業務プロセス）

### 2.1 設計原則

1. **判断の自動化と承認の人間留保を分離する。** 可逆的・基準化可能な判断（一次切り分け、ステージング昇格、レポート生成）はAIエージェントが実行し、不可逆・高影響の判断（本番デプロイ最終承認、Sev1宣言、権限付与）は人間が承認する。
2. **すべての判断基準を数値・条件として文書化する**（PRDおよび外部・内部仕様書のID付き項目として管理）。
3. **すべてのエージェント判断は監査ログに記録する**（誰が・何を・どの根拠で）。

### 2.2 AIエージェント構成（役割の定義）

| エージェントID | 名称 | 置き換える現状業務 | 置き換える理由 |
|---|---|---|---|
| AGT-ORCH | オーケストレーター | （新設）各エージェントのスケジューリング・逸脱監視 | 50プロジェクト横断の制御点が必要 |
| AGT-BLD | ビルド監視エージェント | AR-01のビルド失敗調査（ISS-01） | ログ解析・原因分類は基準化可能で、Claude Codeによる修正案生成まで自動化できる |
| AGT-DEP | デプロイ判断エージェント | AR-01/AR-03のステージング昇格判断・本番承認依頼作成・ロールバック発動（ISS-02, ISS-03） | 判断基準（TH-001〜TH-003）を数値化すれば機械判定が可能。人間は最終承認のみ |
| AGT-INC | インシデント一次切り分けエージェント | AR-04/AR-05の一次切り分け・エスカレーション（ISS-04, ISS-05） | 重大度分類・影響範囲推定は過去事例＋メトリクスから基準化可能 |
| AGT-CHG | 変更管理承認補助エージェント | AR-03の承認資料作成・リスク評価 | 変更内容の差分要約・リスクスコアリングを自動化し、人間の承認判断を高速化 |
| AGT-RPT | 定期報告エージェント | AR-07の報告作成・配信（ISS-07） | プロファイル別HTMLレポートの生成・Outlook配信は完全自動化可能 |
| AGT-SEC | 権限管理・監査エージェント | AR-06の権限申請処理・棚卸し（ISS-06） | JIT権限付与・期限失効・定期棚卸しは規則化可能。付与承認は人間に留保 |

### 2.3 人間とAIの役割分担（意思決定ポイントの再配置）

| 現状DP | To-Beでの扱い | 実行者 | 承認者（人間） |
|---|---|---|---|
| DP-01 PRマージ可否 | AIがレビューコメント・リスク要約を生成、マージ判断は人間 | AGT-BLD＋Claude Code | リーダー |
| DP-02 ステージング昇格 | TH-001充足で自動昇格 | AGT-DEP | 不要（事後通知のみ） |
| DP-03 本番リリース承認 | AIが承認パッケージを生成しTeamsで承認要求 | AGT-CHG＋AGT-DEP | リーダー以上（TH-002） |
| DP-04 ロールバック | TH-003充足で自動発動、事後に人間へ即時通知 | AGT-DEP | 不要（発動から2分以内に通知・Sev2起票し、人間が事後対応。PRD REQ-012） |
| DP-05 一次切り分け・重大度分類 | AIが分類・起票・通知（TH-004） | AGT-INC | Sev1宣言のみ人間（リーダー以上） |
| DP-06 権限付与 | AIが申請を整形・妥当性チェック、付与は人間承認後にAIが実行（TH-007） | AGT-SEC | リーダー（開発・ステージング）／マネージャー（本番・外部企業） |

### 2.4 To-Be業務フロー（概要）

詳細な入出力・API・データ構造は内部仕様書（DOC-INT-04）、ユーザーから見た振る舞いは外部仕様書（DOC-EXT-03）に定義する。ここでは流れのみ示す。

1. **CI/CD**: push→GitHub Actions実行→失敗時AGT-BLDがログ解析・原因分類・Claude Codeで修正案PRコメント生成→メンバーへTeams通知。成功時、TH-001充足でAGT-DEPがステージングへ自動昇格。
2. **リリース**: AGT-CHGが変更差分・テスト結果・リスクスコアを承認パッケージ化→Teamsアダプティブカードでリーダー以上へ承認要求→承認後AGT-DEPが本番デプロイ→15分間の自動監視→TH-003該当で自動ロールバック。
3. **インシデント**: アラート受信→AGT-INCが5分以内に重大度分類（Sev1〜4）・影響プロジェクト推定・GitHub Issue起票→Teams通知→TH-005の時限エスカレーション。誤検知パターン（TH-006）は人間確認付きで自動クローズ候補化。
4. **権限**: 申請フォーム→AGT-SECが妥当性チェック→人間承認→JIT付与（本番は最長8時間）→期限で自動失効→月次棚卸しレポート。
5. **定期報告**: AGT-RPTが夜間バッチでGitHub/監視/インシデントデータを集計→プロファイル別HTML生成→Outlookで配信（メンバー日次、リーダー日次＋週次、マネージャー週次＋月次）。

### 2.5 判断基準（閾値）一覧 ※全文書共通の正定義

| 閾値ID | 定義 |
|---|---|
| TH-001 | ステージング自動昇格条件: 対象コミットのCI全ジョブ成功 AND 単体テストカバレッジ80%以上 AND 静的解析のCritical指摘0件 |
| TH-002 | 本番デプロイ承認: リーダー以上によるTeams承認必須。承認要求から30分無応答でマネージャーへエスカレーション、さらに30分無応答でデプロイ自動中止（ステータス「期限切れ」） |
| TH-003 | 自動ロールバック発動条件: 本番デプロイ完了後15分間の監視ウィンドウにおいて、(a) HTTP 5xx率が5分移動平均で5%超、または (b) p95レイテンシがデプロイ前1時間ベースラインの200%超を10分間継続 |
| TH-004 | 一次切り分けSLA: アラート受信から5分以内にAGT-INCが重大度分類・起票・通知を完了 |
| TH-005 | エスカレーション時限: Sev1/Sev2で当番メンバーが通知後10分以内に応答（Ack）しない場合リーダーへ、20分でマネージャーへ自動エスカレーション |
| TH-006 | 誤検知候補条件: 同一アラートルールが直近30日で3回以上「誤検知」ラベルでクローズ済み AND 今回のメトリクス値が閾値の110%未満 → 自動クローズ候補として人間の確認（24時間以内）に回す |
| TH-007 | 権限のJIT付与: 本番環境権限は最長8時間で自動失効。開発・ステージングは最長30日。外部企業アカウントは全環境で最長90日、更新には再承認必須 |

### 2.6 重大度定義（全文書共通）

| 重大度 | 定義 |
|---|---|
| Sev1 | 本番サービス全面停止、またはデータ損失・漏えいの疑い。宣言は人間（リーダー以上）のみ可能 |
| Sev2 | 主要機能の劣化・一部利用者に継続的影響 |
| Sev3 | 限定的影響・回避策あり |
| Sev4 | 軽微・情報提供レベル |

## 4. 用語集（全文書共通・正定義）

- **エージェント**: 本システムを構成する自律AIプロセス。IDはAGT-。
- **承認パッケージ**: AGT-CHGが生成する、変更差分要約・テスト結果・リスクスコア・ロールバック手順を含む承認用資料一式。
- **JIT権限**: 期限付きで付与され、期限到来で自動失効する権限。
- **プロファイル**: 報告受信者区分。PRF-M（メンバー）、PRF-L（リーダー）、PRF-G（マネージャー）。
- **監査ログ**: すべてのエージェント判断・人間承認を記録する追記専用ログ（内部仕様書SPEC-INT-050番台）。
