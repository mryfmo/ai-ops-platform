# 文書4: 内部仕様書 AIエージェント主導DevOps運用基盤

- 文書ID: DOC-INT-04
- 版: 1.0（2026-07-03）。改訂注記: ADR-0016 採択に伴う改訂（委任裁定 R-03-1）
- 対象読者: 後続実装モデル（Claude Opus 4.8 / Claude Sonnet 5）
- 上位文書: DOC-PRD-02（要件）、DOC-EXT-03（外部から見える振る舞い）。本書の各項目は根拠となるREQ-ID・SPEC-EXT-IDを明記する。外部から見える振る舞いは外部仕様書を正とし、本書は「どう実現するか」のみを定義する。

## 1. アーキテクチャ概要（SPEC-INT-001）

- 構成: イベント駆動。GitHub Webhook・監視アラート・Teams/メール受信を単一の**イベントバス**に集約し、AGT-ORCHが各エージェントへディスパッチする。
- エージェント実行基盤: 各エージェント（AGT-BLD/DEP/INC/CHG/RPT/SEC）は独立プロセス（コンテナ）として稼働し、LLM推論はClaude API（コード修正案生成はClaude Code）を呼び出す。
- 状態管理: エージェントはステートレスとし、状態はすべてデータストア（第3章）に置く。再起動時はイベントバスの未処理イベントから再開する。
- 外部接続: GitHub REST/GraphQL API、Microsoft Graph API（Teams・Outlook）、監視ツールWebhook。

## 2. コンポーネント仕様

### SPEC-INT-010 イベントバス（REQ-025）
- 受信エンドポイント: `POST /v1/events/github`（GitHub Webhook）、`POST /v1/events/monitor`（監視アラート）、`POST /v1/events/inbound-message`（Teams/メール受信の正規化済みイベント）。
- 各イベントは受信時に `trace_id`（UUIDv4）を採番し、以後の全処理・全出力（SPEC-EXT-001末尾等）に伝搬する。
- 受信から各エージェントへのディスパッチ完了まで60秒以内（AC-025a）。超過した場合はイベントを`delayed`状態でキュー保持し、破棄しない。

### SPEC-INT-011 AGT-BLD 処理ロジック（REQ-001, REQ-002 / SPEC-EXT-001, 002）
1. `workflow_run.completed`（conclusion=failure）イベントを受信。
2. GitHub APIで失敗ジョブのログ（最大1MB、超過分は末尾優先で切り詰め）を取得。
3. 分類器プロンプト（PROMPT-BLD-01。プロンプトはリポジトリ`/prompts`配下でバージョン管理する）でClaude APIを呼び出し、次のJSONを取得する。

```json
{
  "classification": "test_failure | compile_error | dependency | infra_timeout | unknown",
  "failed_job": "string",
  "failed_step": "string",
  "log_excerpt": "string (<=20 lines)",
  "confidence": 0.0
}
```

4. `classification`が`test_failure`または`compile_error`の場合のみClaude Codeを起動し、対象リポジトリのread-onlyチェックアウト上で修正diffを生成（書き込み権限を与えない。AC-002b）。
5. SPEC-EXT-001の書式でPRコメントを投稿し、SPEC-EXT-002のTeams通知を送信。全体で失敗イベント受信から10分以内（AC-001a）。
6. `confidence < 0.6` の場合は`classification`を`unknown`に上書きする（過信した誤分類より不明を優先する。AC-001cの検証対象）。

### SPEC-INT-020 AGT-DEP デプロイ状態機械（REQ-003, REQ-010, REQ-012 / SPEC-EXT-003, 010, 040, 041）
デプロイは次の状態遷移のみを許可する。これ以外の遷移を実装してはならない。

`pending → staging_deployed →（承認要求）approval_requested → approved → prod_deploying → monitoring → stable`
分岐: `approval_requested → rejected | expired`（TH-002）、`monitoring → rolling_back → rolled_back`（TH-003）。

- ステージング昇格判定はTH-001の3条件をAND評価。カバレッジはCIアーティファクトのcoverage summary（行カバレッジ）を使用し、80.0%ちょうどは充足とする（AC-003a境界値）。
- 本番デプロイ実行はGitHub Actionsの`deploy-prod`ワークフローを`workflow_dispatch`で起動する方式とし、当該ワークフローはエージェントのサービスアカウントのみが起動できるようGitHub Environments保護ルールで制限する（AC-010a）。
- 監視ウィンドウ（TH-003）: デプロイ完了イベントから15分間、Application Insights / Log Analyticsのquery APIから30秒間隔で5xx率とp95レイテンシを取得。ベースラインはデプロイ前60分の同一メトリクス平均。発動時は直前の`stable`到達バージョンへロールバック（AC-012c）し、Sev2 Issueを起票する。

### SPEC-INT-021 リスクスコア算出式（REQ-011 / SPEC-EXT-010）
`score = min(100, round(0.3*A + 0.25*B + 0.2*C + 0.15*D + 0.1*E))`
- A: 変更行数を0〜100に正規化（2000行以上=100、線形）
- B: 変更ファイルに`/infra/`, `/migrations/`, 認証関連パス（`/auth/`）が含まれる場合100、それ以外0
- C: 直近30日の当該プロジェクト変更失敗率（%を0〜100でそのまま使用、上限100）
- D: テスト結果（失敗0かつカバレッジ80%以上=0、カバレッジ70〜80%=50、70%未満または失敗あり=100）
- E: デプロイ予定時刻が営業時間外（JST 19:00〜翌9:00・土日）なら100、営業時間内0
同一入力→同一出力の純関数として実装する（AC-011a）。

### SPEC-INT-030 AGT-INC 処理ロジック（REQ-015〜017 / SPEC-EXT-012, 015〜017, 030, 031, 044）
1. アラート/外部連絡イベント受信→受付確認送信（SPEC-EXT-031）。
2. 分類プロンプト（PROMPT-INC-01）に、アラート本文＋対象サービスの直近メトリクス＋過去90日の類似インシデント（データストアから類似度検索、上位5件）を入力し、次を得る。

```json
{
  "severity_candidate": "sev1 | sev2 | sev3 | sev4",
  "affected_projects": ["PRJ-xxx"],
  "rationale": "string",
  "false_positive_check": {"matched_rule": "TH-006", "matched": false}
}
```

3. `sev1`はSev1候補としてSPEC-EXT-012カードを送付し、人間が宣言するまでシステム上の重大度は`sev2(candidate:sev1)`として扱う（AC-015c）。
4. TH-005エスカレーションはスケジューラ（SPEC-INT-041）のタイマージョブで実装。Ackイベント受信でタイマーを取り消す。
5. TH-006判定は決定的ロジック（LLM不使用）で実装する: インシデントDBを`alert_rule_id`で検索し、30日以内の`resolution=false_positive`件数と今回メトリクス値を数値比較する。

### SPEC-INT-031 AGT-CHG 承認パッケージ生成（REQ-010, REQ-011）
入力: 対象リリースのPR一覧・diff・CI結果。処理: 差分要約（PROMPT-CHG-01、最大10行）、リスクスコア（SPEC-INT-021）、ロールバック手順（対象バージョンと`deploy-prod`ワークフローのrollback入力値）を組み立て、SPEC-EXT-010カードをTeamsへ送信。承認・却下・期限切れのすべてを監査ログに記録（AC-026a）。承認完了イベントを受けた場合、影響対象の関連企業（`partner_companies`との対応付けはプロジェクト設定で管理）へSPEC-EXT-033のリリース事前通知を送信する（言語選択はSPEC-INT-064に従う）。

### SPEC-INT-032 AGT-SEC（REQ-018, 019, 024 / SPEC-EXT-011, 032, 043）
- 権限モデル: GitHubのリポジトリ権限・Environment権限、およびTeamsゲスト招待を単一の権限台帳（第3章`grants`）で管理。付与・剥奪はすべてAGT-SEC経由でAPI実行し、手動変更を検出した場合は差分をSev3インシデントとして起票する。
- JIT失効: スケジューラが毎分、`expires_at <= now` の権限を剥奪する。
- 妥当性チェック（決定的ロジック）: 申請者の所属プロジェクト一致、理由テキスト非空、同一対象への有効な既存権限なし、TH-007上限以内の期間。いずれか不成立で申請を差し戻す。
- 配信名簿: `recipients`テーブルを唯一のソースとし、AGT-RPTは配信直前に毎回読み直す（REQ-024）。

### SPEC-INT-033 AGT-RPT（REQ-020〜023 / SPEC-EXT-020〜026）
- スケジュール: 毎営業日08:30 JSTに集計バッチ開始、09:00 JST配信（AC-021a）。週次は月曜、月次は第1営業日に追加実行。営業日判定は日本の祝日カレンダー（データストアで管理）に従う。
- 集計: GitHub API・監視API・インシデントDB・権限台帳から`report_snapshots`を生成し、HTMLはテンプレートエンジン（インラインCSSのみ、SPEC-EXT-020準拠）でレンダリング。数値はスナップショットから直接埋め込み、LLMによる数値の再生成は行わない（AC-020bの捏造防止）。文章要約部のみLLM（PROMPT-RPT-01）を用い、要約は数値を改変しない制約をプロンプトで課し、埋め込み前に数値照合チェックを通す。
- 配信: Microsoft Graph API `sendMail`。プロファイル・担当範囲でデータをフィルタしてからレンダリングする（SPEC-EXT-026。テンプレート側でのマスキングに依存しない）。

### SPEC-INT-040 AGT-ORCH
- 各エージェントのヘルスチェック（30秒間隔）。エージェント不応答が3回連続した場合、REQ-029のフェイルセーフを発動: 能動操作（デプロイ・自動クローズ・権限剥奪以外の付与）を停止し、SPEC-EXT-042の通知を送信。権限の自動失効（剥奪）は安全側の操作として継続する。
- 逸脱監視: 各エージェントの出力が本仕様のスキーマに適合しない場合、当該出力を破棄してリトライ（最大2回）、それでも失敗した場合は人間へエスカレーションする。

### SPEC-INT-041 スケジューラ
タイマージョブ（TH-002/TH-005/TH-007/レポート配信）を永続化キューで管理。プロセス再起動でタイマーが消失しないこと。

## 3. データ構造（SPEC-INT-050番台）

データストアはRDB（PostgreSQL想定）。主要テーブル定義（列: 名称/型/制約）:

**SPEC-INT-050 events**: `event_id UUID PK`, `trace_id UUID`, `source TEXT (github|monitor|inbound)`, `payload JSONB`, `status TEXT (queued|dispatched|delayed|done)`, `received_at TIMESTAMPTZ`

**SPEC-INT-051 deployments**: `deploy_id UUID PK`, `project_id TEXT`, `commit_sha TEXT`, `env TEXT (dev|staging|prod)`, `state TEXT (SPEC-INT-020の状態機械の値のみ)`, `risk_score INT`, `approved_by TEXT NULL`, `approved_at TIMESTAMPTZ NULL`, `trace_id UUID`

**SPEC-INT-052 incidents**: `incident_id UUID PK`, `severity TEXT`, `severity_candidate TEXT NULL`, `alert_rule_id TEXT NULL`, `affected_projects TEXT[]`, `github_issue_url TEXT`, `resolution TEXT NULL (fixed|false_positive|duplicate)`, `acked_by TEXT NULL`, `acked_at TIMESTAMPTZ NULL`

**SPEC-INT-053 grants（権限台帳）**: `grant_id UUID PK`, `subject TEXT（社内ユーザーIDまたは外部企業アカウントID）`, `subject_type TEXT (internal|external)`, `target TEXT（repo/environment識別子）`, `level TEXT`, `reason TEXT NOT NULL`, `approved_by TEXT NOT NULL`, `granted_at TIMESTAMPTZ`, `expires_at TIMESTAMPTZ NOT NULL`, `revoked_at TIMESTAMPTZ NULL`

**SPEC-INT-054 recipients（配信名簿）**: `user_id TEXT PK`, `profile TEXT (PRF-M|PRF-L|PRF-G)`, `email TEXT`, `projects TEXT[]`, `language TEXT (ja|en)`, `active BOOLEAN`

**SPEC-INT-055 report_snapshots**: `snapshot_id UUID PK`, `period_start/period_end TIMESTAMPTZ`, `scope TEXT（user/project/global）`, `metrics JSONB`, `generated_at TIMESTAMPTZ`

**SPEC-INT-056 audit_log（追記専用）**（REQ-028）: `log_id BIGSERIAL PK`, `trace_id UUID`, `actor TEXT（AGT-またはユーザーID）`, `action TEXT`, `basis TEXT（適用した閾値ID等。例: TH-003(a)）`, `detail JSONB`, `at TIMESTAMPTZ`。UPDATE/DELETE権限をアプリロールに与えない。保持1年（パーティション月次、13か月で削除）。

**SPEC-INT-057 partner_companies**: `company_id TEXT PK`, `name TEXT`, `region TEXT`, `language TEXT (ja|en)`, `teams_channel_id TEXT NULL`, `notify_emails TEXT[]`

## 4. 外部連携詳細（SPEC-INT-060番台）

- **SPEC-INT-060 手動運用手順（REQ-029/AC-029a）**: エージェント停止時、人間はGitHub Actionsの`deploy-prod`を手動`workflow_dispatch`で起動できる。この場合Environments保護ルールの必須レビュアー（リーダー以上）承認が代替の人間承認として機能する。手順書はリポジトリ`/runbooks/manual-ops.md`に保守する。
- **SPEC-INT-061 GitHub**: App認証（installation token）。Webhook購読: `push`, `pull_request`, `workflow_run`, `issues`。API操作: Issue/PRコメント作成、`workflow_dispatch`、権限付与API、監査ログ取得。
- **SPEC-INT-062 Microsoft Graph**: Teamsアダプティブカード送信・アクション受信（カード操作者のAADユーザーIDを監査ログに記録。AC-026a）、`sendMail`によるHTMLメール配信。
- **SPEC-INT-063 Claude連携**: 分類・要約はClaude API（構造化JSON出力）、コード修正案はClaude Code（read-onlyワークスペース）。プロンプトは`/prompts`でバージョン管理し、変更は通常のPRレビューを経る。
- **SPEC-INT-064 多言語（REQ-027）**: 外部向け通知はテンプレートをja/en両言語で保持し、`partner_companies.language`で選択する。機械翻訳の動的生成は行わない（文言の法的・契約的な揺れを防ぐため）。

## 5. シークレット・セキュリティ（SPEC-INT-070）
- APIキー・トークンはシークレットマネージャ（クラウドKMS連携）に保存し、環境変数経由でエージェントに注入。ログ出力層に既知シークレットのマスキングフィルタを実装（REQ-030/AC-030a）。
- LLMへの入力からシークレットパターン（`ghp_`等の既知プレフィックス、Authorizationヘッダ）を除去するサニタイザを全エージェント共通ライブラリとして実装する。

## 6. 異常系マトリクス（SPEC-INT-080）

| 障害 | 検知 | 自動対応 | 人間への通知 |
|---|---|---|---|
| ビルド失敗 | workflow_run | SPEC-INT-011 | SPEC-EXT-001/002 |
| デプロイ失敗・劣化 | TH-003監視 | 自動ロールバック | SPEC-EXT-040 |
| 承認期限切れ | TH-002タイマー | デプロイ中止 | SPEC-EXT-041 |
| 監視アラート誤検知 | TH-006 | 候補化のみ | SPEC-EXT-017/044 |
| 権限エラー・不正な手動権限変更 | AGT-SEC台帳突合（毎時） | Sev3起票 | SPEC-EXT-043 |
| エージェント停止 | AGT-ORCHヘルスチェック | フェイルセーフ（SPEC-INT-040） | SPEC-EXT-042 |
| LLM出力のスキーマ不適合 | スキーマ検証 | 破棄・リトライ最大2回 | 3回目で担当リーダーへ通知 |
| GitHub/Graph APIレート制限 | 429応答 | 指数バックオフ（初期30秒、最大15分）、イベントは`delayed`保持 | 30分超の遅延でリーダー通知 |
