# DOC-05 内部仕様書: PrjOps AI基盤（実装者向け内部設計）

- 版: 1.0 / 作成日: 2026-07-03 / 依存: DOC-03, DOC-04
- 本書は実装者（Claude Opus 4.8 / Claude Sonnet 5 を想定）向けの内部設計を定義する。各項は根拠となる外部仕様 `[SPEC-EXT-xxx]` および要件 `[REQ-xxx]` を相互参照する。外部から見える振る舞いを変更する場合は必ずDOC-04を先に改版すること。

## 1. アーキテクチャ概要（SPEC-INT-001）

- 実行基盤: report生成は **GitHub Actions**、AGT-03/06の定期処理と検証済みreport配信は既存resident server scheduler、文章生成は **Claude Agent SDK**（ASM-006）。R-02-2によりsecrets・DB operational state・監査・Graph tokenを同じruntimeで扱い、二重化しない。エージェントの実装・保守作業はClaude Code上で行う（PRE-01）。
- エージェント実装: 各AGT（DOC-00 §5）は、リポジトリ `prjops-system` 内の独立したエントリポイント（TypeScript）として実装し、Claude Agent SDK経由でClaude APIを呼ぶ。決定的処理（判定計算・検証・差分計算）はLLMを使わず純粋関数で実装する [REQ-007 AC-007-1]。
- LLMを使う処理は次の3つに限定する: (a) 自由文の構造化（AGT-02）、(b) レポート内の要約文生成（AGT-04）、(c) 重要度引き上げ提案の理由文生成（AGT-03）。モデルは既定で `claude-sonnet-4-6`、(a)で3回連続構造化失敗時のみ `claude-opus-4-8` に昇格して1回再試行。
- Microsoft連携: Microsoft Graph API（アプリケーション権限）。Teams: チャネルメッセージ送受信・Adaptive Card、Outlook: `sendMail`・受信はメールボックスのサブスクリプション（change notification）＋5分間隔のポーリングをフォールバックとする。

## 2. リポジトリ構成（SPEC-INT-010）

| リポジトリ | 内容 | 書込権限 [REQ-033] |
|---|---|---|
| `prjops-data`（private） | 正本データ（§3）。全変更はコミット履歴で監査可能 [REQ-020] | マシンアカウント＋PRF-03 |
| `prjops-system`（private） | エージェント実装・テンプレート・ワークフロー定義 | 開発者＋PRF-03（テンプレ変更はPR必須。DOC-02 §3 PROC-10） |
| `prjops-reports`（private） | 生成済みレポートHTML（配信物の写し）＋配信記録 | マシンアカウントのみ |

## 3. データモデル（`prjops-data` 内、YAML 1ファイル=1レコード）

パス規約: `{collection}/{ID}.yaml`。IDは各スキーマのとおり。共通メタ: `created_at`, `updated_at`（ISO 8601, JST）, `updated_by`（マシン or ST-nnn）。

**SPEC-INT-020 status_update**（進捗アップデート）[SPEC-EXT-011]
```yaml
id: SU-{PJ-nnn}-{YYYY}-W{ww}-{seq}   # seq: 同一週の版番号。最新のみ有効 [REQ-004 AC-004-2]
project_id: PJ-nnn
period: {start: YYYY-MM-DD, end: YYYY-MM-DD}
channel: email | teams | github
reporter: ST-nnn
progress_pct: 0-100           # 整数
self_status: green|yellow|red
achievements: string          # 今週の実績
plans: string                 # 来週の予定
issues: [{ref: ISSUE-nnn}]    # 新規は取り込み時に起票
risks:  [{ref: RISK-nnn}]
complete: true|false          # 聞き返し3回で不成立ならfalse [REQ-005 AC-005-2]
raw_source: path              # 原文の保存先（§7 audit）[REQ-005 AC-005-3]
```

**SPEC-INT-021 project / SPEC-INT-022 stakeholder / SPEC-INT-023 organization** — 属性はREQ-001, REQ-002の列挙どおり（過不足なく実装。追加属性を実装者判断で足さない）。stakeholderは `assignments: [{project_id, profile: PRF-0n}]` で多重所属を表現 [REQ-002 AC-002-1]。

**SPEC-INT-024 issue / risk**: `id, project_id, title, detail, severity: high|medium|low, severity_proposed: {value, reason, proposed_at}|null, status: open|closed, closed_by, closed_reason`。`severity_proposed` の72時間仮適用は AGT-03 が `proposed_at + 72h` を毎日判定 [REQ-008 AC-008-2]。

**SPEC-INT-025 action**: `id: ACT-nnn, project_id, title, assignee: ST-nnn, due: YYYY-MM-DD, status: open|done, reminders_sent: [dates]`。督促間隔（超過当日/+2営業日/+5営業日）は営業日カレンダー（§8）で計算 [REQ-009]。

**SPEC-INT-026 report_job / report**: `id: RPT-{profile}-{scope}-{period}-{recipient}`, `status: generated|verified|pending_approval|approved|rejected|delivered|failed`, `approval: {approver, decided_at, comment}`。状態遷移は §6 の順のみ許可（スキップ不可）[REQ-017 AC-017-1]。

**SPEC-INT-027 削除**: 物理削除禁止。`deleted: true` の論理削除のみ。操作可能者はPRF-03、`delete_reason` 必須 [REQ-021 AC-021-1, DOC-02 §4]。

## 4. 処理ロジック

**SPEC-INT-030 取り込みパイプライン（AGT-02）** [SPEC-EXT-011〜013]
1. 受信（Graph通知/ポーリング/GitHub webhook）→ 発信者をstakeholderマスタと突合。不一致は運用担当へ通知し破棄。
2. 対象PJ特定: 件名のPJ-nnn → 本文中のPJ-nnn → 発信者の担当PJが1件ならそれ、の優先順。特定不能なら聞き返し。
3. LLM構造化: 温度0、SPEC-INT-020スキーマへのJSON出力を強制。必須6項目の欠落判定は構造化後にコードで実施（LLMに判定させない）。
4. 欠落あり→聞き返し送信（回数は `clarify_count` で管理、上限3 [REQ-005]）。充足→YAMLコミット→受理通知 [SPEC-EXT-013]。受信→反映15分以内を満たすため、1件あたりの処理タイムアウトは10分、LLM呼び出しは最大2回。

**SPEC-INT-031 レポート生成（AGT-04）** [SPEC-EXT-020, 021]
- テンプレートエンジン: `prjops-system/templates/{profile}/{lang}.html.eta`（Eta）。共通部品はpartials。プロファイル×言語=10テンプレート（ja/en × PRF-01〜05）[REQ-016]。
- 数値・色・表はすべてコードで算出しテンプレートへ埋め込む。LLMは「結論3行」「トピック要約」等の文章スロットのみ生成し、**数値を含む文はLLM出力から採用しない**（数値はコード算出値をプレースホルダで埋める）→ AGT-07の数値一致検証（§6）を成立させるための設計判断。
- グラフはインラインSVGをコード生成（外部ライブラリ参照禁止）[REQ-010 AC-010-1]。
- 出力先: `prjops-reports/{period}/{RPT-id}.html`。

**SPEC-INT-032 ステータス判定（AGT-03）**: REQ-007の式をそのまま純粋関数 `judge(project, latest_update, issues, actions) -> color` として実装。単体テストで境界値（▲5.0 / ▲15.0ポイント、超過0日/1日）を固定する。

**SPEC-INT-033 コマンドパーサ（Teams）** [SPEC-EXT-014]: 正規表現で定型コマンドを先に判定し、不一致の場合のみLLMで意図解釈→確認カード。権限チェックは実行直前にstakeholderマスタで行う [SPEC-EXT-025]。

## 5. スケジューラ（SPEC-INT-040）

schedule contractをJSTで定義する（ASM-003）。`report-weekly`はGitHub Actions cron、`analyze-weekly`と`track-daily`はresident serverの分単位taskが同じJST gateを適用する:

| ジョブ | cron (UTC) | JST | 対応 |
|---|---|---|---|
| request-weekly | `0 0 * * WED` | 水 09:00 | SPEC-EXT-030 |
| remind-weekly | `0 0 * * FRI` | 金 09:00 | SPEC-EXT-031 |
| analyze-weekly | `0 21 * * SUN` | 月 06:00 | TOBE-04 |
| report-weekly | `0 22 * * SUN` | 月 07:00 | TOBE-05 |
| deliver-weekly | `0 23 * * SUN` | 月 08:00 | SPEC-EXT-022 |
| track-daily | `0 0 * * MON-FRI` | 平日 09:00 | SPEC-EXT-034（祝日は§8カレンダーでスキップ） |
| monthly / quarterly | 毎日00:00 JSTに判定ジョブを走らせ、「第1営業日」「初月第3営業日」に該当する日のみ本処理を実行 | — | TOBE-07, 09 |

AGT-01はresident task内のin-memory stateで失敗時リトライ2回・10分間隔（DOC-02 §5）を適用し、各遷移を追記監査する。仕様はprocess restartを跨ぐretry stateを要求しない。report生成→verify→deliverはGitHub Actions ingestと既存server delivery gateが担う。

## 6. 承認・検証・配信（SPEC-INT-050〜052）

**SPEC-INT-050 承認**（[SPEC-EXT-024], ASM-004）: 状態遷移 `generated → verified → (PRF-01..03: → delivered) / (PRF-04,05: → pending_approval → approved → delivered)`。承認操作はTeams Adaptive Cardのアクション（webhook受信）で受け、レコードの `approval` を更新。24h/48h判定は track-daily とは別の毎時ジョブで行う。

**SPEC-INT-051 検証（AGT-07）** [REQ-019]:
- (a) 数値一致: レポートHTML内の `data-src="{path}#{field}"` 属性付き数値を全抽出し、正本YAMLの値と完全一致比較。
- (b) 権限: プロファイル別禁止語彙・禁止フィールド表（PRF-04: stakeholder氏名、PRF-05: 氏名＋issue.detail＋社内固有語リスト）に対する出現ゼロ検査。
- (c) プレースホルダ: `{{`, `}}`, `undefined`, `null` の出現ゼロ検査。
- (d) 宛先一致: report_jobの受信者とメール宛先の一致。
- NG時: `status=failed`、理由コード（V-A/V-B/V-C/V-D）付きでSPEC-EXT-039通知。

**SPEC-INT-052 冪等配信** [REQ-018 AC-018-2]: 配信前に `prjops-reports/delivery_log/{RPT-id}.yaml` の存在を確認し、存在すればスキップ。送信成功後に記録を書く（記録失敗時は再送許容だが件名 `(再送)` を付与 [SPEC-EXT-023]）。

## 7. 監査ログ（SPEC-INT-053）[REQ-020, 021]

- 実体は `prjops-data` / `prjops-reports` のGitコミット履歴＋ `audit/` 配下の追記型JSONL（原文メール・Teams投稿の写し、操作イベント）。force-push禁止・ブランチ保護で改変不可を担保 [AC-020-1]。保持5年はリポジトリ保全ポリシーとして運用文書に明記 [AC-020-2]。

## 8. 共通ユーティリティ（SPEC-INT-054）

- 営業日カレンダー: 日本の祝日定義ファイル `calendar/jp_holidays.yaml`（年次で人手更新、PRF-03承認のPR）。「第n営業日」判定はこのファイルのみを根拠とする。
- 言語選択: stakeholder.preferred_language。未設定時は organization.country が JP なら ja、他は en（ASM-002）。
- 日時表記: 内部保存はISO 8601＋タイムゾーン。外部表示はSPEC-EXT-027形式。

## 9. シークレット・コスト管理（SPEC-INT-060）[REQ-032, 034, 035]

- シークレット: GitHub Actions Secrets（`ANTHROPIC_API_KEY`, `GRAPH_CLIENT_ID/SECRET/TENANT`）。コード・ログへの出力禁止をCIの秘密検知（gitleaks）で強制。
- LLMコスト: 日次上限 US$20（既定値。PRF-03が設定ファイルで変更可）。各ジョブがトークン使用量を `audit/llm_usage.jsonl` に記録し、日次合計が上限超過なら以降のLLM呼出しジョブを停止して運用担当へ通知。
- 外部通信allowlist: `api.anthropic.com`, `graph.microsoft.com`, `github.com` / `api.github.com` のみ [REQ-035]。

## 10. エラーコード体系（SPEC-INT-061）

`E-{領域}{番号}`: E-ING01 発信者不明 / E-ING02 PJ特定不能 / E-ING03 構造化失敗 / E-GEN01 テンプレート不整合 / E-VER0A〜0D 検証NG(a〜d) / E-DLV01 送信失敗 / E-APR01 承認期限超過。全エラーはSPEC-EXT-039通知の理由コードとして外部仕様の文言に対応付ける。
