# DOC-03 PRD: PrjOps AI基盤 プロダクト要求文書

- 版: 1.0 / 作成日: 2026-07-03 / 依存: DOC-00, DOC-02
- 本PRDの各要件は一意ID（REQ-nnn）と受け入れ基準（AC）を持つ。ACはすべて機械的または手順的に検証可能な形式で記述する。「〜すること」とだけ書かれた要件は存在しない。

## 1. 背景と目的

人手中心のPrjOps業務（DOC-01）は、収集・転記・資料作り分けに週あたり延べ数人日を要し、50件規模が運用限界に達している（ISS-001, 003, 006）。本システムは、収集から配信までをAIエージェント（AGT-01〜07）が主導する運用に置き換え、人間の関与を「判断と承認」に限定する。

## 2. 成功指標（KPI）

| ID | 指標 | 目標値 | 測定方法 |
|---|---|---|---|
| KPI-1 | 進捗報告依頼から正本反映までの中央値 | 24時間以内（AS-IS: 2〜3営業日） | audit_logのタイムスタンプ差分 |
| KPI-2 | 週次レポートのPMO手作業時間 | 0時間（承認作業を除く） | 運用担当ヒアリング（月次） |
| KPI-3 | 期限超過アクションの検知遅延 | 1営業日以内（毎営業日バッチで検知） | audit_log |
| KPI-4 | 配信レポートの数値不整合の報告件数 | 月0件 | 利用者からの指摘記録 |
| KPI-5 | 週次報告の提出率 | 配信サイクルあたり95%以上 | status_update件数 ÷ アクティブプロジェクト数 |

## 3. スコープ

- **含む**: プロジェクト・関係者マスタ管理、進捗収集、分析・判定、課題・アクション追跡、プロファイル別HTMLレポート生成・承認・配信、監査ログ。
- **前提ツール（PRE-01）**: 本システムはClaude Code（開発・保守）、GitHub（正本・実行基盤）、Microsoft Teams・Outlook（利用者接点）の4ツールの上に構築し、これ以外の利用者向けツールを新設しない。
- **含まない**: 会議運営・議事録作成（DOC-02 §3）、契約・請求管理、工数・原価管理、関連企業との非定型交渉。

## 4. 機能要件

### 4.1 マスタ管理

**REQ-001 プロジェクトマスタ**
本システムは、プロジェクトを一意ID（`PJ-nnn`）で管理し、少なくとも次の属性を保持する: 名称、担当リーダー（PRF-02）、担当マネージャー（PRF-03）、参加企業ID一覧、開始日、終了予定日、報告頻度（週次固定）、状態（active/suspended/closed）。
- AC-001-1: 属性が1つでも欠けたプロジェクト登録はエラーになり、欠落属性名がエラーメッセージに含まれる。
- AC-001-2: 100件のプロジェクトを登録した状態で全機能が動作する（PRE-02）。

**REQ-002 関係者・企業マスタ**
関係者を一意ID（`ST-nnn`）で管理し、氏名、所属企業ID（`ORG-nnn`）、プロファイル（PRF-01〜05）、メールアドレス、TeamsユーザーID（任意）、優先言語（ja/en、ASM-002）、タイムゾーンを保持する。企業は国内/海外区分を持つ。
- AC-002-1: 1人の関係者は複数プロジェクトに異なる立場で参加できる（例: PJ-001でPRF-02、PJ-002でPRF-01）。
- AC-002-2: 100社・1,000名を登録した状態で配信ジョブが完走する（PRE-03）。

### 4.2 収集（AGT-02, AGT-05）

**REQ-003 進捗報告依頼の自動送付**
毎週水曜09:00 JSTに、全activeプロジェクトの報告担当者（各プロジェクトのPRF-02、および委任時PRF-01）へ、Teamsメッセージおよびメールで報告依頼を送付する（TOBE-01）。
- AC-003-1: activeプロジェクト50件・報告担当者50名に対し、送付が09:00から30分以内に完了する。
- AC-003-2: 依頼文面は受信者の優先言語（ja/en）で送られる。
- AC-003-3: suspended/closedプロジェクトには送付されない。

**REQ-004 マルチチャネル取り込み**
報告者は次の3チャネルのいずれでも報告でき、システムは受信の都度取り込む: (a) 依頼メールへの返信（自由文可）、(b) Teamsの指定チャネルへの投稿または本システム宛メッセージ、(c) GitHub `prjops-data` リポジトリへの構造化ファイル（YAML）の直接コミット/PR。
- AC-004-1: 3チャネルそれぞれからの報告が、受信から15分以内に正本へ反映される。
- AC-004-2: 同一プロジェクト・同一報告期間に複数報告が来た場合、最新受信のみが有効となり、旧版は履歴として保持される。

**REQ-005 自由文の構造化**
自由文（日本語・英語）の報告から、SPEC-INT-020のスキーマ（進捗率、ステータス自己申告、今週の実績、来週の予定、課題、リスク）へ構造化する。
- AC-005-1: 必須6項目のうち欠落があった場合、報告者本人へ同一チャネルで不足項目を明示した聞き返しが自動送信される。
- AC-005-2: 聞き返しは同一報告について最大3回。3回で充足しない場合は運用担当へエスカレーション通知が送られ、当該報告は「不完全」フラグ付きで正本に保存される。
- AC-005-3: 構造化結果には原文全文が添付保存され、後から突合できる（ISS-007対策）。

**REQ-006 未報告リマインド**
毎週金曜09:00 JSTに、当該週の報告が未提出のプロジェクトの報告担当者へリマインドを送付する（TOBE-03）。
- AC-006-1: 提出済みプロジェクトにはリマインドが送られない。
- AC-006-2: リマインド後も月曜06:00の分析開始時点で未提出の場合、当該プロジェクトはレポート上「未報告」と明示され、直近の提出済みデータが「(前回値)」ラベル付きで表示される。

### 4.3 分析・判定（AGT-03）

**REQ-007 ステータス自動判定**
プロジェクトごとに、次の数値基準でステータス色を機械判定する（自己申告と併記し、乖離を明示する）:
- 危険（Red）: 終了予定日超過、または進捗率が計画線比▲15ポイント以上、または「危険」課題（REQ-008）が1件以上
- 注意（Yellow）: 計画線比▲5〜▲15ポイント、または期限超過アクションが3件以上
- 順調（Green）: 上記いずれにも該当しない
（計画線 = 経過期間÷全期間×100。開始日・終了予定日から算出）
- AC-007-1: 同一入力に対する判定結果は常に同一である（LLMの裁量を挟まない決定的計算で実装する）。
- AC-007-2: 自己申告色と機械判定色が異なる場合、両方がレポートに併記される。

**REQ-008 課題・リスクの重要度スコアリング**
課題・リスクに重要度（高/中/低）を付与する。報告者の申告を初期値とし、AGT-03は「影響の記述にコスト・納期・法令のいずれかが含まれ、かつ対象が複数企業に及ぶ」場合に「高」への引き上げを提案できる（自動確定はしない。確定はPRF-02）。
- AC-008-1: AGT-03による引き上げ提案は、提案理由の文とともにPRF-02へTeams通知される。
- AC-008-2: PRF-02が72時間応答しない場合、提案値が仮適用され、レポートに「仮」ラベルが付く。

### 4.4 追跡（AGT-06）

**REQ-009 アクション期限管理**
アクション（担当者・期限日付き）を管理し、毎営業日09:00 JSTに (a) 期限3営業日前の事前通知、(b) 期限超過の督促を担当者へ送付する（TOBE-10）。
- AC-009-1: 同一アクションへの督促は最大3回（超過当日、+2営業日、+5営業日）。
- AC-009-2: 3回目の督促後も未完了の場合、当該プロジェクトのPRF-03へエスカレーション通知が送られる。

### 4.5 レポート生成（AGT-04）— プロファイル別要件

**共通要件 REQ-010**: レポートは自己完結型HTML（外部CSS/JS参照なし、1ファイル）で生成する。生成スケジュールはJST基準（ASM-003）。全レポートに生成日時、対象期間、レポートID、データ取得時点を明記する。
- AC-010-1: 生成されたHTMLはネットワーク遮断環境のブラウザ（Chrome/Edge/Safariの最新版）で崩れなく表示される。
- AC-010-2: 1ファイルのサイズは2MB以下。

プロファイル別要件は次表で分離定義する（PRE-04）。**共通部分**: ヘッダー（システム名・対象期間・生成日時）、フッター（問い合わせ先・機密表示）は全プロファイル共通テンプレート。**差分**は以下。

| 項目 | REQ-011 メンバー(PRF-01) | REQ-012 リーダー(PRF-02) | REQ-013 マネージャー(PRF-03) | REQ-014 経営陣(PRF-04) | REQ-015 投資元(PRF-05) |
|---|---|---|---|---|---|
| 頻度 | 週次（月曜08:00配信） | 週次（月曜08:00） | 週次（月曜08:00）＋月次 | 月次（第1営業日、承認後） | 四半期（初月第3営業日、承認後） |
| 対象範囲 | 自分が参加するプロジェクトのみ | 自分が担当するプロジェクトのみ | 自分の配下全プロジェクト | 全プロジェクト | 出資対象プロジェクトのみ |
| 粒度 | アクション単位（自分の担当・期限） | 課題・アクション単位＋ステータス | プロジェクト単位＋横断課題一覧 | ポートフォリオ集計（件数・色分布・重要トピック上位5件） | ポートフォリオ集計＋出資対象のマイルストーン |
| 閲覧権限 | 自分に関わる情報のみ。他者の課題は非表示 | 担当プロジェクトの全情報 | 配下の全情報＋エスカレーション履歴 | 全情報の集計値。個人名は表示しない | 集計値のみ。社内課題の詳細・個人名・社内固有情報は非表示 |
| 更新頻度の表示 | 週次スナップショット | 週次 | 週次＋前週差分 | 月次＋前月差分 | 四半期＋前四半期差分 |
| レイアウト要件 | 1画面: 自分のアクション一覧（期限昇順）＋所属PJの色 | 2部構成: PJサマリ→課題/アクション詳細表 | 3部構成: 色分布ヒートマップ→Red/Yellow一覧→横断課題 | 1ページ完結: 冒頭に結論3行、色分布グラフ、トピック5件 | 表紙＋サマリ＋PJ別1ページ。日英切替不可（受信者言語で単一生成） |

- AC-011〜015共通-1: 各プロファイルのレポートに、上表「閲覧権限」で非表示と定めた情報が一切含まれない（AGT-07が配信前に機械チェック。SPEC-INT-051）。
- AC-011〜015共通-2: 上表の頻度どおりのスケジュールで、対象者全員分が生成される（例: PRF-01が200名なら200ファイル）。

**REQ-016 多言語生成**（ASM-002）
レポートは受信者マスタの優先言語（ja/en）で生成する。
- AC-016-1: 同一データから生成したja版とen版で、数値・色判定が完全一致する。

### 4.6 承認・配信（AGT-05, AGT-07）

**REQ-017 承認ゲート**（ASM-004）
PRF-04/05向けレポートは、生成・検証完了後にPRF-03へ承認依頼（Teams＋メール、レポートプレビューリンク付き）を送り、承認操作があるまで配信しない。差し戻し時はコメント必須とし、AGT-04が再生成する。
- AC-017-1: 承認前に配信された事例が発生しない（audit_logで機械検証可能）。
- AC-017-2: 承認期限24時間超過で代理承認者へ、さらに24時間で配信保留のまま遅延通知（DOC-02 §4）。

**REQ-018 配信**
承認済み（PRF-04/05）または検証済み（PRF-01〜03）レポートを、Outlookメール（HTML添付）で各受信者へ個別配信し、併せてPRF-02/03にはTeamsチャネルにも要約カードを投稿する。
- AC-018-1: 1配信サイクル最大2,000通が2時間以内に完了する（100PJ×関係者想定の上限）。
- AC-018-2: 同一レポートIDの重複配信が発生しない（再送時も受信者ごとに1通）。

**REQ-019 配信前検証**
AGT-07は配信前に次を機械検証する: (a) レポート内数値と正本データの一致、(b) 閲覧権限違反の不在、(c) プレースホルダ（未置換変数）の不在、(d) 宛先とレポート対象者の一致。
- AC-019-1: (a)〜(d)のいずれかがNGのレポートは配信されず、NG理由コード付きで運用担当へ通知される。

### 4.7 監査・運用

**REQ-020 監査ログ**
全エージェントの入出力（受信報告の原文、正本更新差分、生成レポート、配信記録、承認記録、エスカレーション）を追記型で記録し、改変不可とする（ISS-007対策）。
- AC-020-1: 任意のレポート内の任意の数値について、根拠となる元報告（原文）まで遡れる。
- AC-020-2: ログの保持期間は5年以上。

**REQ-021 上書き・介入の記録**
人間による判定上書き（REQ-007）、承認、差し戻し、削除操作はすべて操作者ID・日時・理由とともに記録される。
- AC-021-1: 理由未入力の上書き・削除操作はUIレベルで完了できない。

## 5. 非機能要件

| ID | 要件 | 受け入れ基準 |
|---|---|---|
| REQ-030 性能 | 週次サイクル全体（分析→生成→検証）が処理開始から2時間以内に完了 | AC: 100PJ・2,000受信者のテストデータで実測2時間以内 |
| REQ-031 可用性 | 配信ジョブ失敗時、自動リトライ2回＋手動再実行手順が存在 | AC: 障害注入テストで未配信ゼロ（遅延は許容） |
| REQ-032 セキュリティ | 認証情報（APIキー・Graphトークン）は暗号化シークレットストアのみで保持し、コード・ログに平文で現れない | AC: リポジトリ全文検索・ログ検索で秘密情報0件 |
| REQ-033 アクセス制御 | 正本リポジトリへの書込はエージェント用マシンアカウントとPRF-03のみ | AC: 権限設定のエクスポートで確認 |
| REQ-034 コスト管理 | LLM API利用額の日次上限を設定し、超過時はジョブを停止して通知 | AC: 上限額はSPEC-INT-060で定義、超過テストで停止確認 |
| REQ-035 データ所在 | 外部送信されるデータはAnthropic API・Microsoft Graph・GitHubに限定 | AC: 外部通信先のallowlist設定で確認 |

## 6. リリース基準

全REQのACが合格し、パイロット5プロジェクト×2週間の並行運用（人手プロセスと併走）でKPI-1, 4, 5が目標値を満たすこと。
