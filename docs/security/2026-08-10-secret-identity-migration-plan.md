# Secret and identity migration plan

## Decision and boundary

This document is the credential inventory and rotation-order source for P0-T09. It defines the migration from
the repository's current environment-variable and GitHub-secret model to the final architecture. It does not
provision a credential or authorize production access.

The target rules are non-negotiable:

1. In normal operation, only LiteLLM may resolve provider/master credentials. Applications, clients,
   developers, and runners receive a logical model alias plus a short-lived, scoped virtual key. The sole
   exception is the time-bounded, server-side break-glass path defined below; it never exposes a provider key
   to a client or runner.
2. Azure workloads use a distinct managed/workload identity per trust boundary. A shared service identity is not
   a substitute for per-service RBAC.
3. Bedrock uses federated identity and STS temporary credentials. No long-lived AWS access key is stored in an
   application environment.
4. Work IQ is delegated/OBO only. An application credential may authenticate the confidential middle tier, but
   it never substitutes an app-only token for the user's delegated identity.
5. GitHub automation uses repository- and permission-scoped installation tokens. A runner receives only the
   job-scoped token and cannot push `main`, merge, or read a GitHub App private key.
6. Static secrets that remain are versioned in environment-specific Azure Key Vaults, read through a dedicated
   managed identity, and rotated with old/new overlap. Secret values never enter Git, task input, audit detail,
   logs, screenshots, or evidence artifacts.
7. A compromised credential is revoked first as containment requires and is never a rollback target.

Environment isolation is mandatory: dev, staging, and prod have separate Entra applications/identities, Key
Vaults, database roles, Temporal namespaces/credentials, LiteLLM keys, agentgateway registries, GitHub
Environments, and external-service tenants/accounts where the provider supports them.

## Inventory boundary

Current-state sources are `.env.example`, both runtime configuration schemas, the server composition root,
GitHub workflows/actions, the existing [rotation runbook](../../runbooks/secret-rotation.md), and the
[P0-T06 external-service register](2026-08-10-license-service-review-register.md). Target sources are
ADR-0022/0023/0024/0027 and the final-architecture component, deployment, feature-flag, and WBS documents.

The following are identifiers or routing configuration, not credentials: client/application/installation/tenant
IDs, project/repository/team/channel/mailbox allowlists, model aliases, resource IDs, public base URLs, and
non-authenticated internal endpoint names. They remain access-sensitive configuration but do not appear as
independent credential rows. `HEARTBEAT_URL` is included because a provider can encode authorization in its path
or query even though userinfo is rejected.

Workflow-local `GH_TOKEN` and `CALLBACK_SECRET` are aliases of `AIOPS_PR_TOKEN` and
`CODING_TASK_CALLBACK_SECRET`, respectively; they are not additional credentials. The CI-only
`POSTGRES_PASSWORD`/`PGPASSWORD`, `TEST_DATABASE_URL`, and `AIOPS_LOAD_TEST_DATABASE_URL` values address an
ephemeral disposable database and are not production credentials. The server's transitional `GITHUB_TOKEN`
PAT remains a separate matrix row from GitHub Actions' provider-generated job token.

### Audit-location legend

- `APP`: append-only application `audit_log` plus trace/workflow/task/project correlation IDs.
- `AZ`: Azure Activity Log, Container Apps revision history, and Key Vault diagnostic logs.
- `EN`: Entra sign-in, service-principal, consent, and audit logs.
- `GH`: GitHub organization/repository audit log, App records, workflow run, and environment deployment records.
- `LLM`: LiteLLM key-management, spend, routing, and provider-attribution records without prompt/key content.
- `AWS`: STS/Bedrock CloudTrail events and role-session identity.
- `PG`: PostgreSQL authentication/role logs and separately authorized migration evidence.
- `EXT`: the named external provider's restricted audit/change record; no token or request body.

consumer reference back before revocation; after suspected compromise, rollback is fix-forward with a third
credential, never re-enabling the suspect value.

## Rotation invariants

- Prepare → activate → verify → revoke. Revocation never precedes verification except incident containment.
- Rotate the narrow consumer credential before its issuer/root: virtual keys before LiteLLM master/provider keys,
  installation tokens before App private keys, OBO tokens by re-auth before confidential-client assertion changes.
- Container Apps Key Vault references use explicit versions during a controlled canary; promote the verified
  version, then remove/deactivate revisions that still reference the old version.
- Every verification includes one permitted operation and one out-of-scope denial. A health check alone is not
  sufficient.
- Record provider/key IDs, expiry, consumer revision, actor, approvers, before/after state, and result; never
  record secret/token values or reversible hashes.
