# Secret Rotation Runbook

## Purpose and safety boundary

This runbook inventories every secret-bearing setting defined by the server and web configuration schemas,
repository workflows, and the server composition root. It specifies proposed rotation cadence and the
prepare, activate, verify, revoke, rollback, evidence, and incident steps without performing a rotation.

- Never paste a secret into a ticket, pull request, command history, log, audit detail, or this repository.
- Record only the configuration name, owner role, credential version or provider record ID, timestamps,
  verification result, and evidence location. Do not record the value or a reversible encoding of it.
- Secret generation, storage backend, deployment target, approver identities, and provider-console commands
  are **`TBD(HUMAN)`**. This repository does not establish those platform details.
- A rotation is not complete until every consumer has been verified on the new version and the old version
  has been revoked or an explicitly approved rollback window has an expiry.
- For a suspected compromise, use the incident procedure below instead of waiting for the normal cadence.

## Change record required before preparation

Create a restricted change record in **`TBD(HUMAN)`** containing only:

- configuration name and affected consumers;
- reason (`scheduled`, `provider expiry`, `role change`, or `incident`), owner role, approver role, and window;
- old and new credential version/provider record IDs, never their values;
- overlap or outage decision, rollback deadline, and verification plan;
- links to secret-free deployment, workflow, health, audit, and revocation evidence.

Use a distinct version label for the replacement. Confirm backups and rollback data do not contain plaintext
secret values. Before activation, identify every consumer listed in this runbook; partial cutover is a failure.

## Incident rotation procedure

1. Open a security incident in **`TBD(HUMAN)`** and assign the owner role and incident commander role.
2. Stop or restrict affected writes. If active misuse is likely, revoke/disable the suspect credential before
   preparing a replacement; availability is secondary to containment.
3. Identify exposure start/end, consumers, permissions, provider audit events, repository/workflow runs, and
   data or side effects reached. Never copy the credential into evidence.
4. Issue a replacement and follow the relevant per-secret activation/verification steps. A suspect credential
   is never an acceptable rollback target.
5. Reconcile domain state: Graph subscriptions/messages, GitHub deliveries/refs/PRs, coding-task ledger,
   report/import ledgers, database access, sessions, and provider usage as applicable.
6. Revoke every superseded version, remove stale deployment revisions/caches, and document timestamps and
   provider record IDs.
7. Complete the incident review, including why detection occurred, whether the normal cadence was met, and
   whether code must gain dual-key support, automated expiry alerts, or narrower permissions.

## Dependency-aware scheduling

- `DATABASE_URL` is read by server, Web, and the DevOps migration CLI. Record whether runtime and migration
  use the same or separate least-privilege credentials, and rotate all applicable credential references as one change.
- `ANTHROPIC_API_KEY` can span server, Web, and two workflows; an apparently successful single consumer does
  not authorize revocation.
- `GRAPH_CLIENT_SECRET` and `AUTH_MICROSOFT_ENTRA_ID_SECRET` are separate consumer credentials even if they
  belong to Entra app registrations managed by the same role. Do not substitute one for the other.
- `GRAPH_CLIENT_STATE`, `GITHUB_WEBHOOK_SECRET`, `REPORT_INGEST_SECRET`, `XLSX_IMPORT_SECRET`, and
  `CODING_TASK_CALLBACK_SECRET` have single-value validators. Coordinate both sides or explicitly pause traffic.
- `CODING_TASK_CALLBACK_SECRET` also invalidates outstanding confirmation links; drain or replace them.
- Rotate `AIOPS_PR_TOKEN` before a coding-agent window, and use [production gates](production-gates.md) to
  verify that AI-created PRs still trigger CI.
- Graph credential or state failures may force polling; use [Graph subscription recovery](graph-subscription-recovery.md).
- Report-ingest cutovers depend on [report delivery](report-delivery.md), while callback failures depend on
  [coding-task failure recovery](coding-task-failure.md).
