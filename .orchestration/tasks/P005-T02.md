# P005-T02: Change-level Graph notification identity

## Objective

Stop collapsing `created`, `updated`, and `deleted` notifications for one Teams message into one event while still suppressing provable exact redelivery.

## Model selection

- Worker: `gpt-5.6-sol`, reasoning `high`.
- Reason: notification loss and false deduplication are correctness risks; optional Graph fields require conservative trust-boundary logic.

## Primary official evidence

- Teams chatMessage subscriptions support `created`, `updated`, and `deleted`: https://learn.microsoft.com/en-us/graph/teams-changenotifications-chatmessage
- `changeNotification.id` is a unique notification ID but is optional; `subscriptionId`, `resource`, and `changeType` are required for change notifications: https://learn.microsoft.com/en-us/graph/api/resources/changenotification?view=graph-rest-1.0
- `resourceData` is open and can include `id`, `@odata.id`, and `@odata.etag`; do not assume an etag is always present: https://learn.microsoft.com/en-us/graph/api/resources/resourcedata?view=graph-rest-1.0

## Forbidden actions

- No schema/dependency/live Graph/commit/push/PR changes.
- Do not hash `clientState`, secret values, validation tokens, or notification bodies into a persisted key.
- Do not treat missing optional `id`/etag as proof that two notifications are identical.
- Do not collapse multiple `updated` notifications merely because subscription/resource/changeType match.

## Single tasks

1. Extend the accepted notification type only with documented identity/version fields needed for safe dedupe.
2. Add a pure helper that returns a dedupe key only when exact-redelivery identity is provable: prefer unique notification `id`; otherwise use a documented resource version such as `resourceData['@odata.etag']` with subscription/resource/changeType. Return `null` when neither is present.
3. Make the key include change identity so created→updated→deleted for the same message enqueue separately.
4. Preserve the current missing-message/resource rejection and clientState behavior.
5. Add positive/adversarial route tests:
   - created, updated, deleted with distinct notification IDs all enqueue;
   - exact redelivery with the same notification ID enqueues once;
   - two same-type updates with no notification ID/version both enqueue (loss prevention);
   - same message ID in different team/channel/subscription cannot collide;
   - audit detail never contains clientState.

## Acceptance checks

- No `graph:${messageId}` production key remains.
- Exact ID redelivery is skipped; distinct change notifications are not.
- Optional identity absence disables dedupe instead of inventing equivalence.
- Focused tests, server typecheck, formatter, and `git diff --check` pass.
- No live external action occurs.
