# T31: 監査所見 → 逸脱不能な実行計画(チェックリスト付き)への整備

## 目的

受入済み監査 `.orchestration/audit/production_readiness_gap_audit.md`(50 所見、NO-GO)を、後工程のワーカーが**勝手な思い込みや逸脱をできないレベル**の実行計画に整備する。現状の監査は「発見の記録 + 散文の推奨対処 + 粗い 12 グループ順序」であり、DoD・検証手順・スコープ境界・トレーサビリティ・チェックボックスが欠けている。それを埋める。これは read-only の計画整備タスク(製品コードは変更しない)。

## 成果物(2 点)

### 成果物 A: 実行計画本体 `.orchestration/plan/remediation_workplan.md`

全 50 所見(PRG-001〜PRG-050)を**一件も落とさず**タスク化する。各タスクは以下のスキーマを**全項目**埋めること(空欄・「TBD」禁止 — 埋められない項目があるならそれ自体をブロッカーとして明記):

```
### TASK-<PRGID>: <一文タイトル>
- 対応所見: PRG-XXX
- 観点(surface / lens): <監査の 4 面 × 6 レンズのどれか>
- 現状(as-is): <file:line 付きで、今どうなっているか>
- 精査で判明した欠陥: <なぜ製品運用に不足か。監査 Evidence を具体化>
- 改善(to-be): <何をどう変えるか。設計判断が要る場合は選択肢と推奨を明記し、
  ワーカーが勝手に選ばないよう決めておく>
- 許可ファイル/スコープ: <編集してよいパスの列挙。ディレクトリ単位で>
- 禁止事項: <スコープ外編集、モック迂回での見せかけ合格、仕様 ID ヘッダ省略、
  監査ログ改変、依存追加など、その所見固有の禁止>
- 完了条件(DoD、チェックボックス):
  - [ ] <合否が機械判定できる条件を列挙。「動く」でなく「○○が××を満たす」>
  - [ ] mise run ci green(該当する場合)
- 検証手順: <このタスクの修正をどう証明するか。以下を必ず区分:
  verified-integration(このリポジトリ/CI で証明可能。具体的コマンドやテスト名)/
  requires-real-env(PostgreSQL/Docker/実 GitHub/Graph/Anthropic が要る。
  何を用意すれば証明できるかの前提を runbook 粒度で)。
  検証の偽装禁止 — 環境未整備をモックや dev モード迂回で「通過」と装わない>
- 証跡の置き場: <検収時に証跡を書くパス>
- 依存(blocked-by): <先行タスクの TASK-ID。監査の依存順序に整合>
- 仕様トレース: <関連する REQ/SPEC-INT/SPEC-EXT/TH/AC ID。無い所見は
  「新規仕様 ID 採番が必要」と明記(PRG-025 系)>
- ステータス: [ ] 未着手 / [ ] 実装中 / [ ] 検証中 / [ ] 受入済
```

### 成果物 B: フェーズゲート計画 `.orchestration/plan/remediation_phases.md`

監査末尾の 12 タスクグループを、**フェーズゲート付き**の順序計画にする:

- 各フェーズ: 含むタスク、開始前提(先行フェーズのゲート通過)、**フェーズ完了ゲートのチェックリスト**(このフェーズが終わったと判定する条件。例: 「P0 データ基盤 = 実 PostgreSQL に schema.sql + 全マイグレーション適用が CI で緑」)
- CRITICAL 4 件が最初のゲートを構成することを明示
- 各フェーズに「verified-integration で閉じられる範囲」と「requires-real-env でしか閉じられない範囲」を分離記載(後者は go-live チェックリスト PRG-031 に集約)
- ゲート未通過で次フェーズに進めない旨を明記(逸脱防止)

## 逸脱防止の必須要件(これが本タスクの主眼)

1. **思い込みの排除**: 各タスクで設計判断が必要な箇所(例: PRG-017 のデプロイ先プラットフォーム選定、PRG-001 のパーティション戦略)は、選択肢を列挙し推奨を 1 つ決めて書く。「ワーカーが適切に判断」は禁止句
2. **暗黙の前提を明示**: 各タスクの前提条件を書き出す。前提が満たされない場合の分岐(ブロック報告)も書く
3. **検証の区分を強制**: verified-integration / requires-real-env を全タスクで区分。ローカルに PostgreSQL/Docker/実キーが無い事実(監査で確認済み)を踏まえ、実環境検証は前提セットアップ手順とセットで書く
4. **トレーサビリティ**: 50 所見が漏れなく 1 対 1 以上でタスク化されていることを、成果物 A 冒頭のカバレッジ表(PRG-ID → TASK-ID)で証明。監査所見とタスクの対応に穴がないこと

## 制約

- read-only(製品コード・docs・runbook・CI・schema 変更禁止)。書き込みは `.orchestration/` 配下のみ(`plan/` は新規作成可)
- forbidden_actions: code-edits、push、merge、dependency-changes、real-llm-calls、git-checkout/reset
- 監査文書 `production_readiness_gap_audit.md` の所見内容を**改変しない**(計画は別ファイル。所見の再解釈が必要なら計画側に注記)
- 散文の水増し禁止 — チェックリストとスキーマ項目で表現する

## revise 第 1 巡(orchestrator 検証。うち 1 件は orchestrator の指示ミスに起因)

成果物の品質は高い。スキーマ 13 項目は 50/50 充足、`前提/停止条件` と `偽装禁止` も 50/50、設計判断は決め切られており(PRG-017 = Azure Container Apps、PRG-001 = 主キー `(log_id, at)` + default/月次パーティション、代替案の採用禁止まで明記)、引用された仕様 ID 38 件は全て実在した。以下のみ修正すること。

**MUST 1(orchestrator の指示ミスの是正 — 最重要)**

初版タスクファイルで私が「CRITICAL 4 件が最初のゲートを構成することを明示」と指示したが、これは**監査自身の依存順序と矛盾しており、誤りだった**。監査の Recommended Dependency Order は「1. P0 decision baseline: PRG-023/024/025/031 — 『done』を解釈する前に正典要求・NFR・受入責任を確立せよ」を第 1 群に置いている。

現に `TASK-PRG002` は `依存(blocked-by): なし（GATE-0）` としながら、仕様トレースに DevOps `SPEC-INT-011 / SPEC-INT-020 / SPEC-INT-030` を挙げている。**これら 3 件の定義文はリポジトリ内に存在しない**(仕様 ID 295 件中 263 件が定義文なし = PRG-023)。実装者は「AGT-BLD/DEP/INC が何をすべきか」を知る手段がなく、**要求を発明するしかない** — 本計画が防ごうとしている逸脱そのものである。`TASK-PRG004`(PrjOps ランタイム)も同様。

修正方針:

- `TASK-PRG001`(スキーマ正当性)と `TASK-PRG003`(デプロイ経路)は自己完結しており GATE-0 据え置きでよい
- `TASK-PRG002` / `TASK-PRG004` は、それぞれが引用する仕様 ID の定義が確定していることを**開始前提**にする。`依存(blocked-by)` に `TASK-PRG023`(または T32 の復元 + オーナー承認)を明記し、`前提/停止条件` に「引用 ID の定義文が未確定なら実装に着手せず BLOCKED 報告」と書く
- フェーズ計画も同様に是正する。GATE-0 を「PRG-001/003 + 正典ベースライン(PRG-023/024/025/031 のオーナー確立)」とし、PRG-002/004 は正典確定後のゲートへ移す。監査の依存順序と異なる配置を残す場合は、**タスク単位で理由を明記**する(黙って監査と食い違わせない)

**MUST 2(T32 の接続)**

仕様内容監査 T32(`.orchestration/tasks/T32-specification-content-audit.md`)を新設した。その成果物 `.orchestration/audit/specification_content_audit.md` と `spec_reconstruction.md` は、PRG-023/024/025 の直接の入力である。

- `TASK-PRG023` / `TASK-PRG024` / `TASK-PRG025` の `依存(blocked-by)` に「T32 受入済」を追加
- `TASK-PRG023` の DoD 「全既存 ID が text または approved external locator を持つ」は不十分。**外部原本が入手不能な場合の経路が無い**(存在しない文書への locator は監査可能性を与えない)。T32 作業 3 の逆再構成 + オーナー承認を正規の代替経路として DoD に明記し、「実装追認の禁止」(復元は現状記述であり正しい要求とは別物)を禁止事項に加えること
